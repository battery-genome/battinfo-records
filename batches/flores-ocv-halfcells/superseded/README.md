# Superseded records

Records this batch has replaced. They are kept, not deleted, because their published copies are still live and the repo convention is to "preserve old source references when they remain historically relevant, and note what has been superseded" (`docs/versioning-and-revisions.md`).

`v1/` holds record files. `supersede-map.json` holds the complete statement, machine-readable, for all 319 published identifiers - which is what a republish actually consumes. Neither is written by `build_records.py` or `build_bundle.py`; `build_supersede_map.py` writes the map, and `build_bundle.py` rebuilds `records/` from scratch on every run, which is why the retired files were moved out of it.

## supersede-map.json

Generated by `build_supersede_map.py` by joining the published corpus to corpus v3 on natural keys that survive re-seeding (serial number, test name, dataset name, cell-spec model string, public electrode label). Every entry names one published identifier and gives it a status:

| status | meaning | count |
|---|---|---|
| `retained` | same identifier in v3; the record content changed, the identity did not | 154 |
| `replaced` | one successor under a new identifier | 159 |
| `split` | more than one successor: one published identifier named several things | 6 |

By record type:

| published type | records | retained | replaced | split |
|---|---|---|---|---|
| `cell_spec` | 9 | 6 | 0 | 3 |
| `cell_instance` | 95 | 48 | 47 | 0 |
| `test` | 95 | 48 | 47 | 0 |
| `dataset` | 95 | 48 | 47 | 0 |
| `test_spec` | 4 | 4 | 0 | 0 |
| `material_spec` | 9 | 0 | 6 | 3 |
| `material` | 12 | 0 | 12 | 0 |

The 141 re-seeded cells, tests and datasets are not copied into `v1/` as files. Their content is unchanged by v3 - only their identifier moved, because it is seeded from the cell spec - so a file copy would add 141 near-duplicates for information the map states in one line each. The three retired cell specs and the 21 retired material-layer records are different: their *shape* is retired, and those files are here.

`v1/cell-spec/` holds the three cell specs as **published** (from commit `d6d3cf5`, the tree published on 2026-08-11), not as v2 staged them. They are the last records in this batch that name their electrodes by polarity: `positive_electrode` for the working electrode and `negative_electrode` for the lithium metal, which is the convention BIG-MAP/BattINFO#345 replaced.

## v1 - the material layer, retired by the electrode remodel

`v1/material-spec/` (9) and `v1/material/` (12) are the records corpus v1 wrote before BattINFO had first-class electrodes. They are retired by BIG-MAP/BattINFO#342: a material spec describes a **powder**, and none of these did.

- The nine v1 `material-spec` records were *electrode products* (active-material kind x electrode source). They are replaced by 12 `electrode-spec` records, one per electrode design, plus one genuine `material-spec` for the only powder the source identifies (the high Mn/Ni disorder LNMO, `spec/epzg-hf4v-k5bk-nqxe`).
- The twelve v1 `material` records were *coated electrode batches*, carrying the aqueous/NMP processing route as an instance property. They are replaced 1:1 by `electrode` records, with the route moved to the electrode spec where it belongs: for an electrode the route is a design decision, so it is part of the spec identity.

## What happens to the published copies

All 319 published records are live in the Battery Genome registry today and stay live. Retiring any of them is part of the republish, not of this branch:

1. Publish the 25 records the electrode remodel added (1 material spec, 12 electrode specs, 12 electrodes), specs before instances.
2. Publish the 6 new cell specs, then the 47 cells, 47 tests and 47 datasets re-seeded under them - each type after the one it references, as the link-integrity gate requires.
3. Update the 154 retained records in place: same identifiers, new content.
4. Mark the 165 retired identifiers superseded, pointing at the successors in `supersede-map.json`.

Steps 1-4 are a single reviewed operation. Until it runs, the registry copy of this dataset is the v1 shape and the branch is the v3 proposal.
